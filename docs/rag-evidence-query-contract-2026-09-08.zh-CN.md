# 通用取证与查询来源合同：实施与验证

2026-09-08，起点4f6f87b。实现交付，R01语义验收仍开放。本轮按用户要求修复边界，不新增重写Agent、不枚举全部业务、不改变失败的联合权重。

## 根因与实施

1. 取证要求分散，缺少“信息缺口→可用能力→结果能证明什么”的统一原则。新增`application/evidence_query_contract.py`，主Agent规划直接使用通用取证规则，强调历史助手文本不是外部事实证明、用户自述与假设保持原性质、已有适用证据可以复用。业务工具仍由其能力定义说明用途；不添加第二个意图分类模型。
2. 主Agent快捷动作与领域工具的query说明分别维护。两者现在引用同一个QUERY_DESCRIPTION：完整问题可原样保留；上下文消解保留关系、否定作用域、条件和假设；不把预期答案写作既知事实。Schema保证结构，不保证语义正确。
3. 原始消息没有进入检索请求及诊断。AgentContextView在执行上下文边界从current_message写入original_user_message，覆盖同名旧值，不修改输入mapping。主Agent直接工具和领域Agent都沿现有trusted_context传入工具handler，再进入KnowledgeRetrievalRequest及Trace。模型Schema不暴露此字段，额外伪造参数拒绝。没有原始消息的旧调用记None，不伪造为完整query。
4. 原句只供来源追踪，不参与新融合、不改变模型精排问题。相同完整query可复用缓存，但每次Trace重新绑定当前原句，避免缓存携带另一轮的来源。query_mode明确标识RESOLVED/HISTORY；旧variants中的raw标签仍是输入查询分支，不能当用户原句。

没有依靠否定词词表构造所谓语义保证；未接入step-back或自动子问题扩展。前轮联合策略未胜出，冻结排名配置。检索效果问题仍以既有分层证据为准。

## 验证

相关测试198通过、3跳过（依赖条件以pytest输出为准）。新增测试覆盖多个原句形态、运行时源覆盖、主/领域Schema同源、模型伪造字段拒绝、真实handler到请求的传递、缓存命中时原句变化但证据不变。现有RESOLVED跳过对话改写且精排使用完整query测试通过。

12次Flash、0自动重试、2048输出预算；输入70065 tokens、输出728。使用真实ConversationAgent与原生工具选择，注入冻结的对话fixture；未走MemoryLoader、检索、业务执行、最终回答。因此不叫端到端验收。本轮没有同题旧版对照，不能声称prompt提升了多少个百分点。

| 场景 | 观察 |
|---|---|
| 否定发货、短回复消解、条件复合、历史助手断言、话题切换、缩写 | 选中knowledge_search，关键检索意图可见 |
| 寒暄/致谢 | 直接回应 |
| 无商品信息的价格问题 | 追问商品，没有编造商品；但错误地使用英语 |
| 只查退款进度 | 仅refund_status |
| 进度加处理时限 | refund_status加knowledge_search |

工具选择12/12符合这组人工预期，不等于query语义12/12，更不等于回答正确率。假设耳机和相机两例的query保留了条件，但没显式保留“假设”字样：条件式政策检索本身不等于事实断言，本轮无状态写入，不能标成已证明的事实污染；也未证明下游一定保持假设性质，保留此验收缺口。旧礼品卡断言以“是否”为问题重新取证，没有直接确认永不过期。

## 剩余项与交付边界

- 语言一致性出现1条失败；不靠为该题补样例宣称解决。
- 查询语义需要新表达和跨领域验收；这12条不再用作封存。
- 原句诊断来源是当前执行轮，续接轮会是续接消息；完整任务上下文仍由work item及history承担，不能把续接原句当完整目标。
- 真实Memory→Agent→检索→最终答案仍需同案例验证。此次没有新的Recall改善数据。
- 未改变既有发布核验、业务控制与权威判断；原句追踪不自动赋予事实权威。
