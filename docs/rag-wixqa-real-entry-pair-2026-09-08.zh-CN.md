# WixQA 公共真实入口两题对照（2026-09-08）

## 范围和合同

复用完整 6,221 篇 / 11,167 chunk 的隔离 PostgreSQL，冻结开发集顺序前两题，不注入参考答案或手工完整 query。真实 Conversation Agent 自行规划、调用 knowledge_search，经本地 BGE query embedding、PG 混合检索、Flash 精排、compose/verifier 产生回答。两臂向量权重 0.25 / 0.5，其他预算一致；每臂最多 12 次 API，实际各 8 次，共 16 次。文档未重新向量化。

初始默认电商能力范围下两题被 planner 判 OUT_OF_SCOPE，实际 2 次 API、零检索。评测租户现在显式声明 Wix Help Center 支持范围；生产默认不变。新能力 bundle 与中文电商 encoder 的版本绑定不兼容，首次 scoped 运行在模型前失败（0 API）；使用既有 TARGET_ENCODER_ENABLED=false 后由同一 Conversation Agent 规划，两臂一致。这是公共评测域适配，不是通过强制计划或提供答案提高模型成绩。全部失败轨迹保留。

## 结果

| 指标 | 向量 0.25 | 向量 0.5 |
|---|---:|---:|
| 实际进入知识工具并完成回答 | 2/2 | 2/2 |
| 候选文章 Recall（逐题平均） | 100% | 100% |
| 打包文章 Recall（逐题平均） | 75% | 75% |
| 所有标注文章均保留的题数 | 1/2 | 1/2 |
| Flash 调用 | 8 | 8 |

两臂来源身份相同；打包原文与 corpus 偏移、checksum 逐项一致，答案引用 ID 均存在于实际模型可见证据中。该检查不证明语义支持。两题均已有开发用途，不是独立封存验收，不报告整体答案准确率。

编辑网站题两臂实际 query 相同：How can I edit a published website in Wix?。计费题实际 query 不同：0.25 额外提及 payment methods，0.5 使用 billing setup/charges/payment。不能将两臂答案差异完全归因融合权重。

## 已定位的损失与语义边界

编辑题保留了标注文档，两臂均说明编辑后重新发布；0.5 还解释 Save 与 Publish 的区别。对应步骤能在证据中找到，尚未实施独立盲评。

计费题 gold 是计费 FAQ 和退款政策。退款政策在融合候选中分别位于第 3 名和第 8/13 名，但均没有出现在最终 pack。FAQ 的多个片段占据上下文。因此本例不是候选未召回；损失范围在精排和证据选择之间。尚未从核验轨迹确定精排排序与打包各贡献多少，不宣称单一模块根因已关闭。

两份答案都覆盖月费、15% 管理费、额外额度和结转，未覆盖退款政策。原问题很宽泛，标注文章遗漏不能自动等同答案错误。来源本身也包含“订阅额直接转成 ad credit”与“扣除 15%”等需要一起解释的措辞，不能仅以引用合法判断表述无歧义。

## 下一项（R02/R10，预注册）

先零 API 重放已有两题的精排输出、pack 选择和来源，分清退款政策被排低还是被预算/去重删除，同时阅读原参考答案确定必要回答方面。固定 query、现有候选、模型输出和预算，不修改生产策略、不按 gold 强塞文档。指标是逐阶段 article qrel 覆盖与必要信息覆盖，采用条件是发现明确损失机制并有跨案例验证；单例不足以采用“每篇强制取一块”等策略。

保留默认权重 0.25。此前 20 条离线封存样本的打包文章 Recall 55%→67.5% 属于另一项证据，不能写成本次端到端提升。

## 零 API 边界复核补充

已通过 scripts/audit_wixqa_rerank_loss.py 从原模型请求解析全部20个候选，与捕获的生产候选正文逐项一致；模型返回20个唯一合法ID，pack严格等于精排前5。退款政策的位置为0.25第6、0.5第7/8，无token预算或去重丢弃；这是排序加final_k的文章覆盖损失，不是文本截断。

进一步检查 ExpertWritten 第112行参考答案：其中没有退款规则结论。月费、一次性额度、15%管理费、暂停最后一个活动campaign关闭自动续订、管理订阅均可由已保留FAQ支持。因此不得将漏掉退款政策直接记为最终答案错误，也不能据此采用强制文档多样性。

两臂真实ToolMessage中的 E975060ac5af1 / E48d21d94cf4d 包含暂停/自动续订条件，而两份答案均未提到。这是相对参考答案的信息遗漏，非证据不可见；原问题宽泛，尚不能断言线上用户必须得到参考答案的每个细节。应将“参考信息覆盖”和“回答用户明确要求”分别标注，避免过严验收驱动无效检索改动。

接下来以当前已消费公共开发集建立答案要点与支持片段的显式评估口径，先标出参考中的可选扩展与用户明确要求，不增加模型调用或立即改生成prompt。后续小量真实生成才可判断查询消解、检索和答案信息覆盖的净收益。此诊断产物为 rerank-loss-audit.json；默认策略不变。

## 答案要点诊断（事后标注，不作为盲测成绩）

按原参考答案建立9项作者标注：编辑可行性、从dashboard进入编辑器、月费覆盖广告、额外额度不改变订阅、15%/85%费用分配为5个核心点；Edit Site按钮、正确账户、最后一个广告暂停关闭自动续订、管理订阅入口为4个参考细节。此分组是对已看过答案的开发标注，不是数据集官方标签或独立人工盲评。

| 要点覆盖 | 0.25 | 0.5 |
|---|---:|---:|
| 核心点 | 5/5 | 5/5 |
| 参考细节 | 0/4 | 3/4 |

没有将订阅管理与暂停视为当前宽泛问题必须无遗漏覆盖的上线硬条件，也没有把参考以外的正确内容计为错误。新增可选内容是否有依据应单独核验，此覆盖表不能代替所有生成结论的支持性评分。

每项保存答案hash、对应答案片语及实际ToolMessage证据ID，脚本只验证这些见证存在；语义判断是作者标注，缺席判断并非由关键词算法自动证明。脚本score_wixqa_reference_points.py零API复现汇总，reference-points.json保存所有标注。两组query与生成随机性未控制，本次不将3个细节差值归因于权重。

后续公共小量生成采用这一分层口径，先在运行前确定要点和支持来源，之后对两组匿名结果评估；保留article Recall/MRR/nDCG原口径，不将新要点指标替换历史指标。若同一必要信息已可见却未回答，改生成/任务覆盖；若必要信息不可见，回溯召回、排序、打包。默认策略继续保持，暂不新增检索模型或微调。
