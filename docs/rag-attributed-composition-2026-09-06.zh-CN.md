# 混合客服答复的逐段证据合同

既有 expanded20 开发运行中，14 条实际模型消息含期望政策证据，但只有 5 条最终引用该来源并通过知识支持检查。9 条合成虽满足 response/used_claim_ids 的旧结构，正文却缺证据引用；另一条只走业务查询，合成中的无依据跟进承诺绕过了知识专用核验。

## 应用拥有的输出合同

统一 ConversationAgent 仍负责理解上下文、规划订单和知识工具。合成现在返回 segments，每段具有 text、claim_ids、evidence_ids。知识事实由 AllowedClaim 生产者明确标为 KNOWLEDGE_FACT，业务事实保留 FACT，操作凭证与执行状态仍分别为 RECEIPT、WORK_ITEM_OUTCOME。

应用层逐段验证 claim ID 存在、证据属于该段声明的知识事实，且每个使用的知识事实至少有一条证据关联；校验通过后生成可见引用。正文不再承载模型手写的内部 ID 或引用标记。Provider 使用应用拥有的 schema，不能另定义一套输出含义。旧 response/used_claim_ids 模型输出不再被当作新合同接收。

归属合法不代表文字受到支持。最终渲染文字（包括确定性失败提示）继续交给支持性 verifier，并在知识发布前复验来源。业务合成也使用同一个 verifier，依据为原始业务 facts、receipts 和类型化 outcomes，不使用待检查答案或生成摘要证明自己。Verifier 不可用、拒绝或异常时返回业务事实与状态的确定性回退。

独立审查发现回退曾可能重新展示领域 Agent 的 candidate_response，使被拒绝的承诺再次出现。现在共享回退渲染只读取已验证事实、已提交凭证和类型化结果，覆盖合成格式失败、业务核验失败和知识核验失败。支持的确定性事实摘要仍以现有订单状态为主；其他事实保留在运行结果中，回退明确表示无法整理可靠答复。单一领域结果的既有 pass-through 验证边界不在本轮迁移范围，不能据此宣称所有 Agent 正文均已重新核验。

## 低成本固定输入验证

从此前 20 条捕获中提取实际存在的 15 条合成输入。其余五条原规划截断，没有可重放合成输入。历史 v1 输入在评测器中显式迁移知识事实类型和请求版本，保留原捕获；这不是单纯更换模型的实验。

15 次合成＋15 次支持性验证，共 30 次 API 调用：

| 信号 | 结果 |
|---|---:|
| 合法结构并通过应用渲染 | 15/15 |
| 模型支持性检查通过 | 15/15 |
| 含知识证据的案例引用期望来源 | 14/14 |

相对原运行同 14 条有知识输入的案例，期望来源引用由 5 条到 14 条；该差异包含合同、提示和采样变化，没有隔离各因素贡献。它不是 20 条完整入口正确率提升。

audio-defect 仍缺原规划未查询的政策证据。新的合成不再添加原来的跟进承诺，但仍只答订单与退款状态；模型支持性 PASS 不能证明覆盖全部用户目标。

独立人工复核还发现模型核验遗漏的事实语义问题：privacy／receipt 把 delivered 扩写为“已签收”，但订单的确定性映射是“已送达”，输入没有承运方签收事件；preorder 把记录 created_at 称为“下单时间”，但该字段是首次写入订单记录的时间，未证明为实际下单时点。这些是事实含义待核实，不能仅当作表达风格问题。14 条知识回答的核心政策结论有对应原文支持，但这不证明同时输出的业务事实完全准确。return-shipping 额外引用耳机检测规则，当前订单为耳机，不可据此推广为所有商品通用条件。

此重放不执行业务、检索、实时来源复验或发布，不能视作上线验收。完整混合入口复跑另行记录。
