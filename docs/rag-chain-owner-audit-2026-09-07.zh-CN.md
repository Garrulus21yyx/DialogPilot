# RAG 全链路责任边界审计与修复

本轮检查真实 Conversation Agent → knowledge_search → PostgreSQL 混合召回 → LLM 精排 → EvidencePack → Conversation compose → verifier → publication，并检查其上游文本导入、切块、向量身份、来源版本、撤回与缓存。

结论：此前几个失败主要是跨层合同不一致，不能归为“Flash 智力不足”或 chunk 不好。本轮已修复有证据的合同问题，并用生成边界、真实数据库和小规模 Flash 链路验证。**这不是三数据集大规模效果验收，也不是所有潜在错误已经消失的声明。**

## 根因与修复

| 责任边界 | 证据与根因 | 本轮处理 |
|---|---|---|
| Conversation 查询 | Schema 允许省略 resolved_query，编译器有历史时拒绝；调用者不可能从 Schema 得知完整要求 | 四类知识 shortcut 的 Schema 和编译器统一要求完整非空查询；直接工具复用同一知识输入 Schema。业务实体不是全部必填 |
| 日期与时点 | options 接受任意字符串，消费端只接受 aware datetime；日期被错误要求写成时间点 | `policy_date` 表示 YYYY-MM-DD，`as_of` 表示明确带时区时点，两者互斥；运行时按知识库业务时区解析完整日范围 |
| 日内版本边界 | 只选择日初或日末会擅自替用户选版本 | 时间范围贯通 request、SQL、复验和候选缓存；召回来源当日存在版本切换/失效时返回 `AMBIGUOUS / POLICY_DATE_REQUIRES_TIME`，不给部分政策证据 |
| 查询扩展权重 | standalone 等于原查询时，其权重被丢弃；raw 权重为零时可能只剩扩展查询；空白扩展未排除 | 相同基础查询合并权重，丢弃空白扩展；保持基础问题的检索质量占比 |
| 缓存等价关系 | 模型接收原始文本，缓存却对查询 casefold/空白折叠；listwise 候选顺序变化仍命中集合缓存 | 模型相关缓存绑定真实输入；精排键包含有序候选、标题和全文。不会把未经验证的语义等价当缓存等价 |
| 去重 | 仅按 source_id 与字符区间识别重叠，未区分版本 | 同一来源、同一 revision/checksum 才按重叠去重；按待选片段自身被覆盖的比例判断，较大片段包含已选短片段时不能误删新增证据 |
| 发布来源 | 验证来源原文和当前 manifest hash，但没有验证该来源属于该 manifest | 发布前验证来源确实属于当前 collection/generation 的 manifest，再验 checksum、原文位置和撤回状态 |
| 单路召回 | Dense 权重为零，仍可能调用 embedding、执行向量分支 | 生产搜索关闭零权重分支；纯 BM25 在 embedding 完全不可用时仍可工作，串行和并行均验证 |
| 默认策略 | Retriever dataclass 与 Bundle 的默认值存在第二份定义 | Retriever 直接引用 `core/rag_policy.py`，增加跨层默认值一致性测试 |
| 回答接口 | 旧实验遇到自然文本 producer 与 segments consumer 混用 | 当前 fc56b1e 的并发迁移已统一自然文本与证据快照，本轮重新验证；不把这部分全部算成本轮自己的修复 |

`KNOWLEDGE_BUSINESS_TIMEZONE` 由系统配置，默认 UTC，评测语料生效时间也使用 UTC。部署时应按知识库的业务日期语义配置，不能使用服务器所在地或让 Agent 猜时区。日期不等于 UTC 午夜：例如 Europe/Berlin 的夏令时切换日实际可为 23/25 小时。用户只给日期而当日存在版本切换时，需要具体时间。相对日期的开放语言理解仍由 Agent 使用会话时间上下文完成，本轮没有新增自然语言日期解析器。

引用另有边界：政策回答的生成要求使用来源 ID，程序检查已出现引用是否合法。**不能因为手中有知识证据，就强制所有追问和弃答都带引用。** 未实现每一项自然语言结论与引用的确定性证明；语义支持仍依赖 verifier 和评测。

## 实际结果

### 冻结源码、六条真实 Flash 链路

产物：`artifacts/eval/rag-owner-frozen6-2026-09-07/`。

| 项目 | 结果 |
|---|---:|
| 样本 | 6 条中文电商模拟案例 |
| 外部模型调用 | 24 次 Flash，通常每题规划/精排/生成/核验各一次 |
| knowledge_search 成功并获得证据 | 6/6 |
| 运行时 verified | 6/6 |
| 证据原文与 source 字符位置一致 | 6/6 |
| 指定必要证据片段在打包结果可见 | 6/6 |
| 重放模型证据序列化后片段仍可见 | 6/6 |
| 答案含合法来源引用 | 6/6 |
| 端到端延迟 p50 | 4.79 秒 |

逐例人工复核核心政策结论：

- 拆封耳机、非质量原因：不适用七天无理由。
- 质量退货加急运费：加急不报销，标准运费上限十八元。
- 2026-03-01：旧版上限十二元。
- 欧洲区未拆封普通商品第十天：仍在十四日期限内。
- 刻字定制、未拆封三天、非质量原因：命中定制例外。
- 2026-04-01 生效当天：新版上限十八元。

六条核心结论均符合模拟语料，但仍发现表达质量问题：第一条再次询问耳机情况，已有非质量原因上下文时属于多余追问；“有效期至4月1日”的文字可能不够明确地表达右端点不包含，结构化时点筛选和生效当天案例正确。没有把这些文字表现隐藏成“所有维度100%”。

此前相同三条案例为 0/3 合格政策答复（5 次调用，两个规划合同失败、一个 compose 接口错误）；本次相同三条全部完成。这个对照证明已知故障被排除，**不能说答案准确率普遍提升100个百分点**：代码包含并发回答接口迁移，模型输出也有随机性。本轮先后进行3条预检、6条工作区复验、6条冻结复验，合计60次 Flash调用；主要最终结果以最后24次为准。

### 无 API 验证

- 原文切块：固定/结构切分各60份确定种子生成文本，验证所有原文字符都有覆盖、偏移回读严格一致。
- 查询合同：四种知识目标 × 缺失/空白/完整查询；工具/规划/解析边界同构。
- 日期：UTC/夏令时、日期与时点互斥、日内版本切换、生效边界、最大日期溢出的类型化失败。
- 缓存：候选排列全排列、文本变化、查询大小写变化、日期范围变化应区分；未改写时基础查询不失权重。
- 真 PostgreSQL：来源更新、撤回、有效期、地区/商品范围、manifest 成员身份、并行路径与纯BM25无embedding。
- 回答链：非法引用、撤回、无证据/不可用、事实与知识要求分离，以及自然文本合同回归。

最终分组验证：252项单元/合同/生成边界/重放测试通过，另62项来源与检索集成测试通过（使用隔离PostgreSQL）。另2项heldout评测入口测试通过。三个命令的测试文件集合不重叠；没有把开发中重复执行次数累加成覆盖规模。

新增去重性质测试用100组随机来源区间验证：不受预算约束时去重前后原文覆盖一致；修复后打包器版本提升为 `context-packer-v2-revision-coverage`，生产与已提交评测入口同步引用版本常量。源码环境此前依赖传递安装的jsonschema，本轮将运行时直接依赖显式锁定。

## 哪些不是本轮已经解决的事

1. **语义完整 query 无法只靠必填字段保证。** 第一次3条预检中有一条 query 漏写非质量条件，最终答案依靠统一上下文仍正确。冻结6条中拆封问题漏写“非质量”，运费问题漏写“质量原因”，按“查询中显式重述已知条件”的严格口径为4/6（不等于其余查询不可检索）；最终答案仍为6/6核心结论正确。运费问题还把 shipping 写成销售渠道。已为共用 Schema 补齐销售渠道/地区/商品范围的语义描述，但不把描述修改宣称为语义问题已消失；它未再追加API调参。应持续独立统计查询语义、过滤条件和最终答案。
2. **PDF/HTML/OCR 不属于当前来源导入合同。** 当前支持 text/markdown/JSON 中的文本内容，超预算 Markdown 原子结构明确拒绝；没有暗中增加另一套解析器。
3. **本轮没有产生新的大样本 Recall/MRR/nDCG 提升。** 上轮300题本地结果仍是同预算打包182→208、MRR .4736→.584、nDCG .5078→.6117；是本地CE实验，不能冒充当前生产LLM精排的效果。
4. **parent-child 和动态融合不是默认上线项。** 既有同预算实验没有稳定胜出，继续保留简单生产策略；并行代码可配置，当前测试证明行为与容量边界，尚不证明部署环境 p95 吞吐增益。
5. **MTRAG/WixQA 已锁定但未完成外测。** 本次六条不是封存集，不替代跨数据集泛化验收；还不能给“RAG全链路已完全收敛”的状态。
6. **程序来源校验不等于语义证明。** 模型仍可能误解隐含条件、增加含糊表述；引用存在、hash一致不意味着每项结论必然有依据。

## 参考与验收边界

2026-09-07 查阅的 [LangChain 官方 retrieval 文档](https://docs.langchain.com/oss/python/langchain/retrieval) 支持 Agent 使用现有知识库工具，也区分查询增强、检索验证和回答验证。此处沿用成熟的责任划分，不新增 RAG Agent。动态路由、额外拆分调用或层级召回是否更优，要用同预算数据证明；它们不能修复 Schema/时间/缓存的程序合同缺口。

可复现：`scripts/run_rag_tool_calibration.py --full-chain --scenario ecommerce-full --max-api-calls 40 --model <BGE-M3 snapshot> --output <new-directory>`，固定所有 ModelRole 为 deepseek-v4-flash/none、provider deepseek，设置隔离测试 PostgreSQL 的 `TEST_DATABASE_URL`。数据库生命周期由脚本管理，Redis使用临时实例。重放 `PYTHONPATH=. .venv/bin/python scripts/audit_rag_full_chain_probe.py <result-directory>` 不调用模型。

复现限制：未显式设置生效时间的模拟来源仍采用实际导入时刻，因而重新执行时 revision/generation ID 可能变化；本次保留原始调用、来源checksum及时间，不将重复执行宣称为逐字节一致。

源码证据：最终API运行冻结587个Python文件；`snapshot-source-sha256.json` 记录实际源码身份。随后零权重分支/默认值归一/极端日期类型化错误/去重覆盖性质与打包缓存版本由无API测试验证，另恢复共享Schema中的业务范围字段说明；不声称对API答案额外贡献。全局关闭仍需冻结策略后的外测与独立语义审阅。
