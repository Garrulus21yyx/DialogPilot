# 业务读取证据的语义与版本切换

混合 RAG 回答曾把订单记录 created_at 写成实际下单时间，把 delivered 扩写为签收事件，并把 refund_window_missing 推成退款窗口已过期。原始业务拥有者分别只保存记录写入时间、订单快照状态及退款提交前置检查结果，这些扩写没有依据。

## 拥有者修复

services/customer_operation_views.py 定义业务读取投影。订单工具现在输出 order-view-v2：内部 created_at 转为 record_created_at，状态提供业务拥有者的 status_label，并携带字段含义。数据库、内部 Order 和写操作版本控制保持原合同；user_id 继续不对模型公开。更新时间明确为记录更新时间，不能据此声称发货或签收发生时间。确定性回答也复用同一套状态标签。

退款资格读取输出 refund-eligibility-v2。eligible 继续表示当前是否允许提交操作，写操作的前置校验未放宽；assessment_status 将缺少窗口数据标为 INSUFFICIENT_DATA。reason_description 和 assessment_scope 明确该检查不判断赠品、商品例外或退款金额政策。订单金额也不等于已批准或已到账退款金额。

语义字段随真实 ToolResult 进入 FactRecord.value_json，并被合成与核验读取。它们帮助理解数据，不是自动产生的新业务事实；正确政策仍须由知识检索取得。

## 兼容性

注册表只允许每个 producer 有一个当前版本，本次切换到 v2，没有放宽多版本规则。活跃 producer 与测试夹具已迁移；历史捕获保持原版本，评测中若转换旧输入必须显式指定 --business-view-v2。

旧 v1 无法按当前注册表新签发证据。更广的影响是全策略 fingerprint 变化：旧 fingerprint 的序列化凭据（包括未改 producer 的凭据）恢复时也会被现有机制判为 WIRE_EVIDENCE_INVALID。需要按新策略重新获取证据；不能把旧凭据直接改版本号或把历史捕获当成当前有效证据。没有修改历史数据或数据库模式。

## 实验结果与局限

四个已消费合成输入经过业务投影后重放，合成＋核验共八次 API 调用。四条均通过结构和模型核验；gift-return 正确说明窗口未知，没有再断言已过期；elliptic 使用“已送达”，preorder 未将记录时间称为下单时间。

但模型把不少字段说明照搬进答复，包含不必要的快照与记录存储解释。随后增加合成提示，要求字段语义用于解释、正文只包含用户需要的内容；同四条再次重放八次调用，均通过模型核验，但三条仍有多余说明。这是尚未解决的表达质量问题，不能把四条 PASS 当作完整产品验收。gift-return 也仍缺赠品政策检索，只能表明还需政策依据。

两轮合计十六次 API 调用，没有重跑 embedding 或检索。此实验同时涉及证据视图及合成输入变化，是开发诊断，不是 heldout，也不是检索算法收益。完整 Agent 入口尚未重跑本次 v2 版本。

## 验证

- 本地相关测试 126 通过、4 项数据库条件测试跳过。
- 隔离 PostgreSQL 测试 41 通过，覆盖真实工具语义输出、权限／启动校验、证据解析以及应用入口与持久结果边界。
- 属性组合覆盖真实 _eligibility 对订单状态、窗口缺失／过期／有效与已有退款申请的输出，验证前置布尔值保持、INSUFFICIENT_DATA 单独表达。
- 独立复核确认迁移范围与版本拒绝行为，并指出全策略 fingerprint 的兼容性影响。

下一步仍需修复混合问题的目标遗漏，并抑制不必要的字段讲解；之后使用新的混合入口用例验证，整体 RAG 目标保持未完成。
