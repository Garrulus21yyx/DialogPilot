# E09：23题失败根因核查

核对起点31f982a；冻结E06检索捕获与E08答案，不新调用API、embedding或精排模型。逐题重新检查80题候选/排序/原文位置/工具可见内容，并用本地tokenizer检查1560个实际精排输入。此次完成诊断，不声明修复或整体质量关闭。

## 结论：原来的数字是“丢失位置”，不是完整根因

原来“2超时＋16精排后证据不全＋5生成未完整”的统计成立。但16题不能全归因于精排模型：其中`cx-09-4`实际独立查询没有生成成功。故优先处理可证实的输入语义缺口，再验证结构切块和多证据选择，而不是单纯增大TopK或恢复微调。

## 1. 查询：历史已给到，但模型没有完成指代消解

`cx-09-4`的实际改写调用：

- 历史：“组合装只退一瓶，退款按什么价格、赠品怎么处理、运费谁承担？”
- 当前：“如果我还不能确认是否满足这些前提，请列出需要核实的条件、相关例外和后续处理步骤，不要直接认定我符合条件。”
- 模型返回：当前句原样，缺少商品与三个具体需求。
- 没有API异常、JSON异常或截断；`rewrite_error=None`。本次不是统一Context注入漏掉历史，模型确实看到了它。
- `KnowledgeRetriever`发现standalone与raw一致，只保留raw分支；精排也使用这句。`rewrite_fallback=True`记录了未得到不同改写，但没有证明这是语义正确的单轮查询。

候选20碰巧仍包含三条正确证据；精排后条件排第8、费用排第13，Top5只保留赠品条款。不能因候选命中就认定Query质量通过。

另两条存在部分需求压缩：`cx-06-4`改写未显式保留起保日期与申请材料；`cx-29-4`未显式保留锁紧步骤。它们仍保留宽泛“后续处理步骤”，没有做反事实模型实验，不能量化这项遗漏造成的排序损失。

**责任与修复合同**：查询转换层负责把历史中已明确的目标和本轮需求保留为独立检索问题；运行时需要区分“本来独立，无需改变”和“仍依赖这些/上述等指代，解析未完成”。相同文本本身不是普遍错误，不能全局禁止原样输出；也不能只靠出现产品关键词认定所有需求完整。后续开发验收应对齐完整需求与否定作用域，保留失败状态和原历史，不把合法JSON算作成功消解。

第8/13名是前述Query失败题；其余15题各缺一条，均在第6/7名。17条缺失中15条为费用/材料/操作内容，2条为适用或操作前提。

以耳机`cx-02-1`为例：Top1条件片段含20个二级标题；Top2例外片段含12个标题；Top3/4/5是另外多种商品规则，不含本题任何必要条款。耳机退款金额、耗材扣除及运费的正确片段排第6。相关内容并未在切块时丢失，而是多个商品混在每块中，模型对整块主题相关性的判断不能保证三方面证据组合完整。

**已证实机制**：`LocalKnowledgeReranker`对每个query/chunk独立打分，按分数排序；`KnowledgeRetriever`交给packer按final_k=5取内容，没有针对缺失方面的集合覆盖保证。不是8192输入被截断，不是原1200字符问题复发，也不是打包再丢掉正文。

**尚属假设的部分**：混合主题造成相关性稀释是合理解释，但未在本轮改变chunk或模型作因果对照，不能声称结构切块已验证有效。44个无gold槽位也不等于44段全部毫无语义价值。

**下一项最小实验**：在开发规则上保持来源/偏移/模型和最终5/2600预算，比较按商品小节保留标题与完整表格行的child，与当前跨商品混合chunk；先验证条件、例外和操作原文均可回溯，再测完整证据集合。若仍存在重复相关块占位，再验证有界的分方面检索/证据选择；不按测试gold挑片段。精排整体42→62有价值，不能直接去掉。

## 3. SQL：确认全范围逐请求计算机制，历史负载原因未证实

原日志确认这两题是词法SQL的750ms statement timeout。当前后端BM25实现先物化适用范围全部片段，再逐片段`unnest(lexical_terms)`计算TF、DF和平均长度，最后才取TopK。即使最后仅返回20，也不表示数据库只计算20条。

Dense与lexical在同一事务；lexical异常使本次调用返回UNAVAILABLE，先完成的Dense没有作为部分成功返回。因此是检索服务不可用，不能算知识不存在。

此次只读检查发现原隔离数据库已不存在；没有当时EXPLAIN ANALYZE、CPU/IO/锁等待记录。可以证明SQL路径和超时行为，**不能断言两次超时只由这个执行计划导致，或者已经排除共享机器负载**。

下一步在隔离开发库采集相同scope的执行计划及耗时分布，评估预计算词频/倒排候选访问，同时保持scope内统计及授权一致；不要直接提高750ms、取消过滤或扩大重试。若要允许单路降级，须在检索结果合同中显式表示部分成功与成本，不能把半份结果静默标成完整成功。

## 4. 生成：2个明确内容问题＋3个严格完整性扣分

- `cx-03-4`：三条证据齐全，但漏清水测试不算制作饮品；历史恰好涉及通水试机，是真实必要边界遗漏。
- `cx-11-4`：资料给了R72频段、组网型号和设置步骤，却说没有相关前提与步骤，是错误拒答。原生成prompt将资料不足导向整段弃答，没有显式需求覆盖记录；这是当前合同的诊断缺口，不能仅凭prompt归因所有模型误判。
- `cx-18-1/3/4`：P84不支持答对，地区与安装也答对；没列P82/P83支持，按原三条款完整标准扣分。属于评分严格程度与产品需求的边界，不应与错误兼容承诺等同，也不为提高分数事后改口径。

下一步生成开发验收按“用户要求的方面→已答/缺证据/遗漏”逐项检查，证据齐全时应组织回答；确实缺证据时说明具体缺项，不整段臆断资料无关。模型自报覆盖仍须独立评估，不能再把核验PASS当答案正确率。此轮没有修改生成prompt或新增核验Agent。
