# DialogPilot 项目讲述与简历逐条讲解

> 本页按简历五条DialogPilot经历串起源码、取舍与验证，当前实现核对至c91eae2。配套：[架构]({{ "/architecture.html" | relative_url }}) · [追问]({{ "/interview-guide.html" | relative_url }}) · [RAG]({{ "/rag-study.html" | relative_url }}) · [证据]({{ "/handbook-evidence.html" | relative_url }})。

## 30秒开场

DialogPilot是一个智能电商客服系统，支持政策咨询、订单查询与售后处理。我重点解决复合诉求漏执行、长会话丢依据和业务操作中断后难以确认结果的问题。系统用主Agent处理自然对话、直接查询和领域委派，任务图协调领域Worker调查与准备业务动作，工具结果可归档回读，退款等写操作通过审批和对账执行；业务状态和已声明字段直接按回执展示，知识解释按需核验后持久交付。我还把检索、上下文和业务交互分别评测，保留失败实验来判断优化到底作用在哪个环节。

## 三分钟项目介绍：STAR 口述版

“我做的这个项目叫 DialogPilot，是一个智能电商客服 Agent 平台，主要处理政策咨询、订单查询和售后操作。

最开始，我关注的是客服里比较复杂的多轮请求。比如用户说：‘帮我查一下配送情况，如果能退货，告诉我运费谁承担，但先别提交退款。’这一句话既需要查询订单，又需要检索退货政策，还带着明确的操作限制。如果后面用户继续补充信息或修改要求，系统就需要一直记住哪些问题已经解决、哪些条件还缺、哪些操作还没有授权。

所以我给自己定的目标是：让 Agent 能完整处理这种复合诉求，在长对话里保留必要依据，同时把业务操作控制在明确的权限范围内。围绕这个目标，我主要做了三方面工作。

首先是任务规划和多 Agent 协作。我没有让每个领域 Agent 各自理解整段对话，而是由主 Agent 保留用户的完整目标和约束，简单查询直接处理，需要业务判断和修改的任务再委派给领域 Agent。任务会带上依赖关系、工具权限和执行预算，独立的查询可以并行，结果统一汇总。这样即使一个环节缺少信息，也能保留其他已经完成的结果，并明确告诉用户还差什么。

其次是上下文和业务执行。长任务里，订单详情和检索结果会不断累积，所以我把工具原始结果先归档，再清理过期观察、压缩历史，同时优先保留当前目标和最新工具结果。需要细节时可以按引用回读。对于退款这类写操作，我会把批准范围绑定到具体参数和目标版本；如果调用超时，先确认业务到底有没有发生，再决定后续处理，避免直接重试造成重复操作。另外，我最近把确定的业务结果交回代码展示：工具声明金额、单位和地址字段，系统按对应回执直接呈现；知识解释和跨来源综合再用模型组织与核验。准备好的独立操作也会组成一张完整确认清单，让用户一次批准明确范围，之后逐项保留执行结果。

第三是 RAG 和评测。我把检索和最终回答分开检查：先看必要证据有没有被召回，再看经过精排和上下文打包后，模型是否真的看到了这些证据，最后检查回答是否完整、有依据。三套外部数据分别用来观察政策条款、多轮追问和产品指引的检索表现，再用中文电商模拟集验证组合场景。

优化时，我会根据失败发生的位置决定改哪里。比如有些问题已经召回了正确材料，但最终放进上下文的证据不完整，这时候继续扩大候选池不一定有效，要检查排序和打包策略；如果检索到了不适用的政策，就需要把渠道、地区等适用条件贯通到检索链路。

目前，在已经用于回归的 80 道中文模拟题上，模型实际可见的完整必要证据覆盖率是 77.5%，严格完整且有依据的回答比例是 71.25%。我会把这两个结果分开报告，因为找到证据和正确回答之间还有一段差距。这个项目里，我最主要的工作，就是把任务规划、工具执行、证据核验和失败评测串起来，让每次优化都能找到具体问题，也能通过后续回归检查有没有解决。”

## 最新调整如何讲

“这次我主要简化了模型和代码之间的分工。以前连已经准备好的审批清单、工具返回的金额和地址，也可能再让模型组织并核验。实际上，这些数据的来源、单位和操作范围已经明确，再解释一遍反而可能漏字段或把‘已提交’说成‘已到账’。

所以现在，审批清单直接从已准备操作集合生成，受支持的业务字段由工具声明展示规则；运行时核对来源、版本和回执后直接输出。知识解释、政策适用性和混合问题仍按需生成与核验。我也把面向主Agent的对话约束和领域执行规则分开，避免协调者误把自己当执行者。简化后各层职责更明确，而且这些路径不需要额外模型调用；整体任务收益还需要单独评测。”

实现核对至c91eae2。操作集合已提交，不能继续写作“工作区进行中”；它的初始两项修改已在task22实际执行，但后续对话导致最终状态失败。策略隔离和工具字段展示后的整任务效果尚未重测。

## 第一条：分层决策与多 Agent 协作 {#resume-collaboration}

**可以直接讲：**“客服请求经常同时包含查订单、问政策和修改业务，而且用户会在下一轮补信息、反悔或者追问。我先看当前会话有没有待补输入、审批和未完成目标，防止把‘好的’当成一个全新任务。简单查询由主 Agent 选择只读工具，业务变更则把完整目标与约束交给领域专家；应用再把计划编译成带依赖、权限和预算的WorkPlan。独立读取可以并行，ResultBoard保留每项结果和缺口。”

例如“查物流，符合退款条件就帮我申请，但先告诉我费用”：物流状态和退货政策可能来自不同来源，是否允许申请也不能只看一个领域标签。主 Agent 保留“先告诉费用”这一条件，领域调查具体规则和订单状态，准备后由当前审批合同决定是否进入执行。不能因为用户表达了修改意图，就把未来所有动作视为批准。

**为什么这样拆：**状态续接解决已有任务的身份；领域分类缩小候选范围；主 Agent处理会话与委派；领域Agent理解操作条件；Compiler检查可执行的合同。LangGraph协调依赖，不替代授权。相同业务对象的相关修改应整体委派，避免在主层拆成两个看似独立、实际有状态约束的写任务。

**Encoder怎么讲：**简历写“快速路径”，代码提供的是可选六域加DEFER路径。接受结果仍经过同一Policy，低置信和复杂等待状态走主链；示例默认关闭，不能把候选试训当线上收益。面试重点是拒识、适用范围和为什么状态优先，而不是仅报模型名字。

**要验证什么：**同一输入有两个独立目标时不能漏掉一个；失败只阻断相关依赖；并行完成顺序不改变汇总；批准伴随独立问题时两者都保留。当前职责与状态绑定的限制见[架构第五至六节]({{ '/architecture.html' | relative_url }})。

## 第二条：上下文工程与长程执行 {#resume-context}

**可以直接讲：**“我把模型上下文当成一个有预算的工作区。先保存工具原始结果，再逐步清理旧观察、压缩历史；当前目标和最新完整工具批次优先保留。模型需要细节时读取归档页，而不是重新执行业务工具。这样压缩可以减少反复输入，又保留证据回查路径。”

一次大订单结果如何处理：原始结构和证据身份进入归档；模型看到可用摘要、引用及证据目录；接近输入预算时清理较旧ToolMessage，再对历史语义压缩。预算包含system、工具schema、历史、当前任务和输出预留，而不是只截用户聊天文本。最新工具批次需要整体保留，避免assistant.tool_call没有对应ToolMessage；受保护部分也太大时，才用有界卸载与回读处理。

**结构断言能证明什么：**消息配对没有破坏、当前目标保留、归档引用可读、页边界正确、没有重新执行业务工具。**语义评审能检查什么：**要求与否定是否保留、有没有发明批准/完成事实、来源权威是否混淆、已完成和剩余工作是否准确。仓库评测脚本明确有required_preserved、no_invention、authority_preserved、progress_preserved四个维度；16次合成开发检查不等于真实长会话泛化保证。

**32%和41%要如何回答：**输入Token降低应固定同一批任务、模型和完成判据，把摘要与后续回读新增调用也纳入约定口径。重复查询减少应先定义“无新目标、无有效刷新需要、没有新结果的业务重查”，不能把合法状态刷新或对账也计作坏循环。本PDF里的32%/41%来自此前模拟写作口径，本轮未找到对应真实配对报告，不能拿16次摘要检查替代其证据。

表达机制时可从“工具原文→模型可见内容→压缩后内容→回读内容”四份材料复核。防循环则是另一层：观察进展判定与调用/时间预算共同限制无效执行，不能把上下文压缩本身等同于死循环检测。

## 第三条：场景化 RAG 与证据核验 {#resume-rag}

**可以直接讲：**“电商客服既要找政策，也要理解多轮追问和定位产品指引。我先用三套外部数据分别测试这三种需求，再用中文电商资料检查地区、渠道、商品等适用范围和跨来源必要证据。检索结果经过融合、精排和预算打包后，继续检查模型实际看见的正文；最后单独评答案有没有完整使用这些证据。”

**三种需求对应三个单位。** Doc2Dial检查文档中的必要条款是否完整覆盖；MTRAG检查多轮目标下的相关片段；WixQA检查产品支持文章定位。简历中的300/35/20是各自实验样本量，不是合计355题的统一成功率，也不代表官方全量排行榜。参数、查询来源、语料和开发/留存状态都应跟随报告解释。

**从77.5%讲到71.25%。** 中文80题的完整可见证据为62/80；严格完整且有据的回答为57/80。其余23题包括2题上游超时、16题可见必要证据缺失、5题证据齐全但生成漏答或不当弃答。两项指标属于证据阶段与生成阶段，不能把5题差额简单解释成所有生成错误，也不能把77.5%称任务完成率。参考与语义复核并非独立人工Gold，80题也已消费为回归。

**FTS术语如何说清。** PostgreSQL全文检索是词法侧技术范围；项目已有自写PG BM25评分路径与原生ts_rank_cd候选，原生FTS不等于BM25。Dense/Lexical权重与raw/standalone查询权重也不是同一维度。具体generation、Bundle与报告决定当次采用哪个后端和参数，不因简历写FTS就抹掉选型差异。

**优化动作和结论分开。** Metadata贯通针对错误适用范围；标题切块针对条款边界与混合商品片段；精排策略针对候选有但Top5缺失；原生FTS对照针对SQL可用性。候选更快但Wix质量回退时不采用。不要只背指标，要能从失败所在阶段解释为什么改这一层，详见[RAG专题]({{ '/rag-study.html' | relative_url }})。

## 第四条：受控业务执行与故障恢复 {#resume-execution}

**可以直接讲：**“写操作的关键是批准什么、实际执行什么、发生了什么，三者要一致。我把提案绑定到具体参数、目标版本和操作标识，批准后执行侧再次核对绑定。PG操作记录通过CAS迁移状态，成功回执可以重放；超时导致结果未知时先对账。checkpoint负责执行位置，业务账本负责副作用事实，客户响应还通过序号和ACK单独记录。”

要能讲三个故障窗口：执行前进程退出，后续应从有效状态继续；执行已提交但回执传输失败，后续应查询同一操作而非再写一次；业务与回答已落库但连接断开，客户端应续取既有回答。数据库事务只能保证其覆盖范围内的原子性，不自动回滚外部业务调用。

**补足简历没展开的交付问题：**提案存在不等于已经成功展示给客户。已提交修复61a9b88由approval_presentation_due统一判断新版本或未发布提案是否需要展示；即使主规划给出普通回复，未送达的待办也要按持久范围重新组织。回答失败的降级文本保留等待状态，不再仅凭空ResultBoard说“没有结果”。状态提示仍不是审批条款，也不能授予执行权限。

**当前已提交的简化：**同一领域准备好的独立动作形成一个批准集合，由确定性范围卡展示；每项仍有自己的operation_key和回执，部分失败不抹掉已提交结果。结果展示进一步使用ToolDefinition声明的字段路径、单位和标签，身份/版本/回执匹配后直接显示金额、地址和状态。未知字段或独立解释需求保留模型路径，范围卡和受支持结果不需要作者/核验器再判断一次。详见[架构回答路径]({{ '/architecture.html' | relative_url }})。


## 第五条：自动化评测与失败归因 {#resume-evaluation}

**可以直接讲：**“我把检索质量、回答质量和业务任务成功分开测。RAG保存每层候选和实际可见证据；上下文用结构断言加语义评审；业务交互通过τ³适配真实应用入口和外部环境工具，用原生评分检查目标状态和动作。失败后从公开对话、工具调用、内部状态和核验输入输出建立证据链，再针对负责该含义的模块修复。”

例如task22：早期版本识别出两处地址修改，却只准备一个提案，还出现审批展示和核验协议失败。操作集合迁移后，首次两处修改已经一次确认、实际执行；但接着用户只想恢复账户地址，主Agent两次选择普通回复，后续对话扩大成两处都恢复，最终ENV=0、ACTION=1、ALL=0。这说明动作覆盖与最终状态必须分开评。随后代码拆分conversation_policy/business_policy，并直接展示受支持业务结果；合同测试不能替代尚未进行的完整任务复测。

**如何沉淀回归：**保存脱敏原始输入、代码/模型/Registry身份、预期合法状态与必要副作用；先构造可确定检查的状态回归，再复用原失败完整快照检查作者/核验，最后在预先固定的新任务上检验交互。旧失败重放只能说明该故障是否恢复；新鲜验收必须有未用于调参的数据。误拒绝、协议失败、用户退出和环境不可用分别记录。

**50条任务76%怎么讲：**PDF写了这一结果，但本轮在相关报告、summary与manifest范围未定位到能支持该口径的50任务报告。若是单次二元任务统计，应有50个固定task/seed与38个通过记录，并明确ENV/ACTION/ALL中的哪项；如果按重复run或平均reward统计，分母与公式又不同。当前已核对的task22失败不能推出总体76%为假，也不能为它提供证明。网页保留这项为“简历声明，报告待对应”，不自行补实验细节。
