# 审批回复：完整状态、一次表达、原操作续接

本次修改只涉及审批表达与公开引用，不改变执行权限、工具调用、金额计算、
读结果有效性或 TaskGraph 的调度规则。

## 数据流

```text
已准备操作 / PendingApprovalState + 业务事实 + 独立任务结果 + 待补信息
  → ResponseAssembler 保存完整证据快照
  → Conversation Agent 一次组织完整回复
  → 既有核验检查这条完整回复与同一快照
  → 绑定原 scope_key → Publication 发布
用户批准 → 既有批准消费与执行路径 → 原操作执行 / Receipt
```

删除了 `approval_presentation.py` 原始参数卡片和递归拆分审批结果的路径。
不再出现“先去掉待审批操作让模型解释，再追加一份机器参数确认”的双重表达。
核验不决定执行资格，不要求重复内部编号或逐字地址；它检查用户所见内容是否
正确解释已准备变更、必要付款条款以及尚未执行的状态。

补信息与审批可以同轮出现。生成和核验同时看到两者；补信息不扩大批准范围。
纯补信息仍可直接发布已绑定的自然问题，不新增模型调用。已经发布的同一审批
继续由现有 `approval_presentation_due` 控制，不因普通状态询问而再次索要批准。

## 证据与公开引用

完整快照保留来源、操作身份及凭证，用于核验、审计和 Publication 绑定。
模型适配入口使用 `composition_evidence` 投影：移除已知事实/凭证信封中的
追踪编号，保留业务对象、参数、时间、执行状态和关联；不对业务载荷递归脱敏，
不修改用户消息或删除商品字段。

`public_citations` 仅从当前知识证据和仍有效的复用知识证据导出。
订单状态、金额和办理结果不需要公开引用内部 `call_id` 或 Receipt ID。
这不是事后正则清洗，也不是新增一轮“要不要引用”的模型判断。

## 失败与恢复

生成失败或核验不通过时，原操作集合仍保存在原状态中；状态说明不能取得
`approval_operation_key`，因此不能冒充可批准的确认请求。既有回复恢复重新
生成表达，不重新准备或执行业务动作。核验指出可修订问题时，继续使用现有
最多一次回复修订；修订前后的完整证据指纹必须相同。

旧的未发布 `PREPARED_SCOPE_RENDERED` 回复不再是合法审批交付结果，应重新
生成回复；已保存的业务操作、批准身份和 Receipt 格式未改变。没有保留旧卡片
作为另一条可用回复路径。
